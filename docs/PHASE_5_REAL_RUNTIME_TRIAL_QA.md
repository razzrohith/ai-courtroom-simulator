# Phase 5 – Real‑Runtime Trial QA

## What changed
- Added a **pure runtime core** (`src/orchestration/trialRuntimeCore.ts`) that contains only the orchestration state‑machine logic, without any UI, React, or Vite dependencies.
- Created a **QA harness** (`src/orchestration/qaRuntimeHarness.ts`) that exercises the core in a deterministic, head‑less fashion.
- Added a **QA‑only TypeScript config** (`tsconfig.qa.json`) that compiles only the two core files to an isolated `.qa-build` directory.
- Updated the **QA script** (`scripts/qaTrialFlow.mjs`) to:
  1. Perform static code‑base checks.
  2. Run the standard type‑check and production build.
  3. Clean the stale `.qa-build` folder, compile the harness, and dynamically import it.
  4. Exit with status 0 when every check passes.

## Why `trialRuntimeCore.ts` exists
The full application bundles a large UI graph (React, Vite, provider graphs). Importing that into Node caused ESM/CommonJS mismatches and pulled in browser‑only code. `trialRuntimeCore.ts` isolates the **business‑logic core** (state handling, transcript, verdict creation, helpers) so it can be run safely in a Node environment.

## Why `tsconfig.qa.json` exists
- Keeps the main `tsconfig.json` untouched (production build stays unchanged).
- Guarantees the QA compile step emits **ES2020** modules into `.qa-build`, a separate folder that never interferes with the normal `build/` output.
- Limits compilation to the two core files, making the QA build fast and deterministic.

## Why `.qa-build` is used
- Prevents accidental overwriting of the production `build/` directory.
- Allows the Node script to import the compiled harness via a simple relative path (`../.qa-build/...`).
- Keeps generated QA artefacts isolated and easily cleanable.

## How `npm run qa:trial` works
1. **Static checks** – verify required source‑code patterns (duplicate‑summary guard, objection categories, evidence‑discipline, etc.).
2. **Type‑check & production build** – ensure the app still compiles.
3. **Compile QA harness** – `npx tsc -p tsconfig.qa.json` produces `.qa-build/orchestration/qaRuntimeHarness.js`.
4. **Run real‑runtime QA** – dynamically import the harness and execute `runRealRuntimeTrialQa()`.
5. **Exit code** – `0` on success, `1` otherwise.

## Static checks vs. runtime shared‑core checks
- *Static checks* guarantee that the source contains the required guards, instruction comments, and configuration.
- *Runtime checks* (inside `qaRuntimeHarness.ts`) validate the **behaviour** of the core:
  - deterministic initialization,
  - transcript entry validity,
  - incremental sequence numbers,
  - evidence‑reference handling,
  - duplicate final‑summary guard,
  - verdict field population,
  - reset/restart invariants,
  - overall state validation.

## Why this is a shared‑runtime‑core QA (not full E2E)
Running the full browser/controller stack in CI is fragile and slow. By testing only the core orchestration logic we get:
- Fast, deterministic CI runs.
- Full coverage of the business‑logic state machine.
- No need for a headless browser or UI rendering.

## Known limitations
- Does **not** test UI rendering or client‑side integration.
- Uses a deterministic mock case; custom cases are not exercised here.
- Any changes to the core API must be reflected in the harness (documented).

## Manual QA checklist
- Run `npm run qa:trial` locally.
- Verify that each `PASS …` line appears and the final line reads `🧪  REAL RUNTIME QA RESULT: ALL CHECKS PASS`.
- Ensure the script exits with status 0.
